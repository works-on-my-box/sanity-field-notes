Field notes — symptom → cause → rule, from an unattended browser-automation stack

An SPA panel renders a cached list first and updates later; read until stable

2026-09-02 · Puppeteer#spa#stability#scraping#dedup

Symptom

A dry run read a conversation card as Client: ... 1:50 PM although our reply You: ... 4:43 PM had been in the thread for 18 minutes and was visible as the third message in the same tab; a re-read 4 s later showed the current preview.

Cause

The panel draws from a local cache and only then refreshes with the API response. 'Cards appeared' is not 'cards are current': the same trap as lazily loaded labels, but here the cost is a stale dedup key and a signal late by one whole cycle.

Rule

Read such lists until they stabilize: after the first non-empty read, re-read every 2 s until two consecutive reads match (not sooner than 6 s, not longer than 25 s) and take the last non-empty read. Test a new parser on a live page where you know in advance what should be last.
