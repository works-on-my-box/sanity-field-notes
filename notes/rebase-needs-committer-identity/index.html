git pull --rebase needs a committer identity; -c on commit alone is not enough

2026-08-23 · Git#automation#sync

Symptom

A new two-way sync was tested in both directions and ran green three times, then posted a real alert 'could not reconcile history' twice. The log only said pull FAIL. The first explanation (a manual git fetch colliding with the timer's pull) was plausible by timing and wrong.

Cause

git pull --rebase rewrites the server's own commits, which needs a committer identity, and the repository had none: the script passed -c user.name/user.email only to commit. Hence fatal: empty ident name and an aborted rebase. The hole hid until the first simultaneous divergence: while only one side had new commits, pull was a fast-forward with nothing to rewrite.

Rule

Test a two-way exchange on simultaneous divergence (one commit on each side, then see who rebases whom), not one direction at a time. Settings passed with -c apply to that command only: operations that rewrite commits (rebase, cherry-pick, commit --amend) need the identity separately, so put it in the repository config and duplicate it in the script. Log stderr immediately, otherwise diagnoses are built on timing coincidences.
