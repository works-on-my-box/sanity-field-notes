pgrep -f and pkill -f match the shell that runs them; find processes by port

2026-09-25 · Shell#pgrep#pkill#ssh#background

Symptom

(a) One ssh command both launched a second Chrome and checked 'already running?' with pgrep -f "chrome-form[s]": the check said yes, Chrome did not start, and the final kill $(pgrep -f ...) killed the shell itself (ssh exit 255). (b) pgrep -f "ssh -i ... .*setsid nohup" returned three PIDs, one of them the command itself (exit 144). (c) An hour later pkill -f "chrome-form[s]" sat in one command with a path containing the same word; the shell matched and died. Separately, ssh 'cd ~ && DISPLAY=:99 setsid nohup google-chrome ... &' never returned until the ssh was killed.

Cause

pgrep -f compares the pattern with the full command line of every process, including the shell that invoked it. The bracket trick (chrome-form[s]) only avoids matching the pattern text itself; the same word elsewhere in the same command matches, and a regex with .* matches itself. ssh hung because cd ~ && ... & backgrounds the whole list in a subshell that keeps the ssh channels open until Chrome exits.

Rule

Do not look for your own processes with pgrep -f/pkill -f at all: stop the second Chrome by the PID of the port listener (pid=$(ss -tlnp "sport = :9223" | grep -o "pid=[0-9]*" | head -1 | cut -d= -f2); kill $pid); find local processes by name (ps -eo pid,comm,args | awk '$2=="ssh" && /.../'). Background launch over ssh: cd ~; <command> >/dev/null 2>&1 </dev/null & sleep 1; echo launched (no cd ~ && before the backgrounded command); check readiness in a separate call by http_code.

Supersedes A wait loop built on pgrep -f matches its own command line and never ends.
