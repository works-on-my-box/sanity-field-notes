Field notes — symptom → cause → rule, from an unattended browser-automation stack

An ssh -L tunnel from WSL binds only WSL loopback; add a second bind on *

2026-09-02 · Windows & WSL#ssh#novnc#wsl#background

Symptom

To let the human click a button on the server's Chrome, a noVNC tunnel was needed. The first command with pkill -f "ssh ... -L 6080" killed the tool's own shell (exit 144). The tunnel -L 6080:127.0.0.1:6080 listened only on WSL's 127.0.0.1 and it was unclear whether a Windows browser would reach it; about 65 minutes were spent waiting, and timeout ... node wait.js; echo exit=$? in the background always printed 0.

Cause

A pkill -f pattern matches the bash -c of the tool itself. A local ssh forward binds to WSL's loopback by default, and Windows sees WSL ports through localhostForwarding only sometimes. A long human wait is normal, not an error.

Rule

Terminate processes by PID from ss -tlnp/pgrep -x, never pkill -f <string>. Bring the noVNC tunnel up in the background with two binds at once (-L 6080:... and -L '*:6081:...') and give the human one URL plus a fallback; close by PID afterwards. Wait for the human with a poller that holds no lock (a lock expires in 5 minutes), one factual message per 15 minutes; do not read the exit code of a background command, print the result in words (MODAL GONE / TIMEOUT).
