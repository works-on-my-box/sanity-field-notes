Field notes — symptom → cause → rule, from an unattended browser-automation stack

Judge a secret by what it opens when stolen, not by where it is stored

2026-08-23 · Git#secrets#tokens#deploy-keys#automation

Symptom

The setup was called safe by the formal test 'the token is only in .env, mode 600, not in git, not in backups', all true. The question 'what does this token open?' showed a classic token with repo, workflow scopes opening every repository of the account, including an unrelated private one, on a rented VPS where a headless model reads untrusted text every 15 minutes.

Cause

'Secrets only in .env' is a rule about leakage, not about privileges. It silently assumes the secret has the right scope, and on a machine running automation over untrusted input that assumption is the hole. The token was also reused: issued months earlier for publishing demos, then handed to the sync job because it was at hand.

Rule

For any secret on an automated machine ask not 'where is it' but 'what can be done with it if read', and trim it to exactly what is needed. For git that is a per-repository deploy key, not an account token: it does not open the API at all. Test the narrowing by refusal (try reaching a neighbouring repository), not only by success. A secret that has been on a rented machine counts as compromised: revoke, do not migrate.
