A migration is not done while the old machine can resurrect daemons at login

2026-08-22 · Windows & WSL#migration#autostart#windows-startup#scheduled-tasks#daemons

Superseded. The current rule is Renaming inside the Windows Startup folder does not disable autostart.

Symptom

After moving the pipeline to the server, the laptop daemons were stopped and no processes remained. A review found a live .vbs in the Windows Startup folder: at the next login the laptop would have started a second copy of the pipeline.

Cause

Processes were killed, not the mechanism that starts them. Autostart is a separate entity that survives stopping daemons and powering off, and is visible only in its own place (Startup folder, scheduler, systemd enabled, cron).

Rule

The last step of any migration is to disarm autostart on the old machine, checked in the old platform's own terms (Windows: Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup" and Get-ScheduledTask). Disable by renaming (.disabled-<date>) rather than deleting, since returning to the old machine is also the rollback plan. The cost of skipping it is concrete: two pollers fighting over the same API (409) and two auto-submitters acting twice on one item.
