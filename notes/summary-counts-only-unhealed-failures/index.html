A nightly error summary must count only failures that were not healed by retries

2026-09-12 · Linux services#logging#alerts#retries#stdout#summary

Symptom

The morning summary said 'errors in logs: 3 (3 kinds)': a FAIL: RENDERER_STUCK from both monitor.out and runs.log, and a poll FAIL fetch failed. The user forwarded them two nights in a row. Nothing was lost: the search was re-read by retry 13 s later and the poll succeeded 15 s later.

Cause

nightErrors took every FAIL line. Both self-healing mechanisms log FAIL before retrying: true about the attempt, not the outcome. monitor.out is the stdout of the same log() that writes runs.log, so each monitor error appeared twice as two kinds.

Rule

An alert to a human counts only what was not healed: for every retry mechanism the summary looks at the outcome (the next line of the same request) and lists healed failures separately with a count. When adding self-healing, teach the summary its outcome in the same change. Do not rewrite logs for the summary: logs are facts about attempts, interpretation belongs in the summary. Before aggregating several logs, check whether one is a copy of another.
