A test double without side effects hides state bugs in the mocked thread

2026-09-06 · Node.js#testing#mocks#idempotency#regression

Symptom

An audit ran the reply engine with a stub where the sent message is appended to the thread as ours; a human's 'ok' after a hold then failed with 'thread changed since the decision': the key took the last message of the thread at all, while the pending key was built from the client's message. The existing regression (8 green checks) never saw it: its stubbed thread returned the same two messages whatever was sent.

Cause

The stub modelled only the input (reading the thread) and not the consequence of its own output (what was sent becomes part of the thread); the human step lived in another process whose path was not stubbed at all.

Rule

A test double must change state the way the world does: the sent text is appended to the thread as our message, and after each send the scenario runs the next human step on the same key. Compute idempotency keys and 'thread unchanged' from the last message of the counterpart, not the last message overall.
