Probes that write to the database poison the 'after' run; use a fresh seed

2026-09-29 · PostgreSQL#rls#ci

Symptom

In the run script the 'before the fix' probes (the attacker making herself owner and admin of another project) ran on the same data as the 'after' probes: in the capture the attacker still saw 4 tasks and UPDATE 1 after the fix, while the text said 2 tasks and UPDATE 0. Noticed by a fact-checker comparing every number against the run file, not by the author or editor.

Cause

Policies stop new leaks but do not roll back rows already inserted; CI only checked the error texts 'after'.

Rule

Writing probes only on a fresh seed (fresh before the fix); CI asserts both states (the 'before' leaks must succeed: UPDATE 1, INSERT 0 1; 'after' must refuse with UPDATE 0); every published number comes from one captured run of the final scripts, never 'roughly the same'.
