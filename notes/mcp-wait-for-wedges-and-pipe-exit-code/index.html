A cancelled MCP wait_for wedges the server; `curl | head` hides curl's exit code

2026-09-02 · Coding agents#curl

Symptom

A wait_for (waiting 4 minutes for a human step) went to the background and was stopped with TaskStop; afterwards evaluate_script and even list_pages hung for 120 s each, although curl /json/list on the CDP port answered instantly and the tab sat on the right page. Separately, if curl ... | head -c 300; then echo UP printed ALREADY UP with the port closed, and the MCP immediately answered Could not connect.

Cause

The MCP server executes calls sequentially: TaskStop removes the task on the client side, but inside the server the wait keeps running and holds the queue until its own timeout. In a pipeline if looks at the exit code of the last command (head), not curl.

Rule

Do not hang a human-step wait on an MCP wait_for: poll with short calls or, more reliably, with a plain puppeteer script over CDP that does not depend on the MCP; after a wedged MCP call do not count on that MCP for the rest of the session. Check a port only with curl -s -o /dev/null -w '%{http_code}' compared to 200.
