Field notes — symptom → cause → rule, from an unattended browser-automation stack

A chat UI renders the message before the server answers; trust the response

2026-09-18 · Web forms#verification#puppeteer

Symptom

A reply was typed and sent; the script checked that the text appeared in the thread and printed OK. Under the text stood Couldn't send your message. Try again, and POST /inbox/conversations/messages had returned 403. The client received nothing; it was caught by reading the output, not by the check.

Cause

The frontend draws the message in the thread immediately, before the server replies. Failure is visible only as a separate retry element under the text. The check measured rendering, not delivery.

Rule

Success of a send is only the server response: the POST returns 201 and no retry element is present. Text in the thread proves nothing. On a 403 do not press retry blindly: reload the thread, make sure the message is absent, and send again. General rule: a UI action is proven by the server response or the state after reload, not by what the frontend drew.
