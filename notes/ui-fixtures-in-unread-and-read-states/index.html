Fixtures from a read item miss the unread counter; dedup keys on volatile fields

2026-09-17 · Puppeteer#scraping#fixtures#dedup#selftest

Symptom

The messages poller recorded the client's first message as 1 and put room_xxx|1 into the dedup memory. The next single message from the same client would have produced the same 1 and been treated as already seen, with no reply and no alert.

Cause

parseRoom took the preview as the last line of the card. The fixture had been captured from a room after the thread was opened, so it had no unread counter. The dedup key (room + preview) was built on a field that coincides across different events.

Rule

Capture UI parse fixtures in both states: unread and read, before and after the action. Never build a dedup key on a field that can repeat across events (a counter, Yesterday, an empty preview). Verify the first live event of a new pipeline field by field against the source, not just by outcome.
