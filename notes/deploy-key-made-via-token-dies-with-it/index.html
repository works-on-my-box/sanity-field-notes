A GitHub deploy key added via the API dies with the token that created it

2026-08-23 · Git#deploy-keys#tokens#ssh

Symptom

Access was narrowed (deploy keys instead of an account token), tested by refusal and success, and the owner was asked to revoke the token. A minute after revocation the server reported it could not sync; ssh with the key answered Permission denied (publickey): revoking the classic token removed both deploy keys, because they had been added through the API with that token.

Cause

Acceptance checked the radius of the new access (where the key reaches and where it does not) and never its dependence on the old secret. The order was the reverse of the safe one: revoke first, then learn that the new path hung on the revoked one.

Rule

When replacing access, first make sure the new path was not created by the secret being revoked and will survive its revocation (for GitHub: add deploy keys by hand in the repository's Settings, Deploy keys, not via the API with a token; a key added in the UI belongs to the owner). Consider access replaced only after the old secret is revoked and the new path is re-tested. Also check ~/.ssh/config and ssh -T git@github.com before generating yet another key.
