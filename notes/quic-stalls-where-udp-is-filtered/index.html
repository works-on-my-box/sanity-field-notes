Field notes — symptom → cause → rule, from an unattended browser-automation stack

HTTP/3 over filtered UDP costs ~30 s per request; Chrome never marks QUIC broken

2026-08-27 · Chrome & DevTools Protocol#quic

Symptom

Poll hangs followed one pattern: first request reads, the second hangs 60 s (Navigation timeout), context reset, one request lost: 40 of 93 polls one day, 50 of 85 the next. A recovered tab stuck for 4.5 minutes on Waiting for <site> to respond. Evidence (rendered page, 'renderer did not answer in 5 s', curl 403 in 1-2 s, Chrome at 10-20% CPU) pointed nowhere for two days.

Cause

Resource Timing of the recovered tab: the document's requestStart - fetchStart was 270 s, i.e. the request sat in Chrome's queue; static assets over h3: p50 27.9 s, p90 31 s at a 1.5 KB median, the same over h2: p50 2.4 s. Outbound UDP is filtered from this address, yet the profile's Network Persistent State had alt-svc h3 for every host and an empty broken_alternative_services: Chrome kept retrying QUIC. A silent renderer and a request waiting on a stalled connection look identical from outside.

Rule

For a hung navigation ask about the protocol and timings first (performance.getEntriesByType('navigation'|'resource'): nextHopProtocol, requestStart - fetchStart, responseStart), not just whether the renderer is alive. Where UDP is filtered, disable QUIC explicitly (--disable-quic) instead of trusting the broken-alt-svc logic. Verify afterwards: no h3 in timings, static p90 under 0.2 s, polls 9/9 in 60-90 s.
